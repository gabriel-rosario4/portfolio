## The problem

The first version worked beautifully in demos and disappointed in use. Not
because the answers were wrong — because they were *unverifiable*. Users had no
way to tell a well-sourced answer from a fluent guess, so they stopped trusting
both.

The redesign optimised for a different target: not "is the answer good?" but
**"can the user check the answer cheaply?"**

## Why pure vector search wasn't enough

Dense embedding search is excellent at finding conceptually related passages
and unreliable at finding exact ones. Users asked both kinds of question, often
in the same session:

- *"What's our policy on refunds after 30 days?"* — semantic; embeddings win.
- *"What does error PGX-4021 mean?"* — lexical; embeddings routinely miss the
  one document containing that literal string.

Embedding search fails the second case in the worst possible way: it returns
confident, plausible, adjacent documents rather than nothing.

<Callout tone="insight" title="The retrieval failure that matters">
An empty result set is a good outcome — the system can say "I don't know". A
set of *related but wrong* documents is the dangerous one, because the model
will dutifully synthesise a fluent answer from them. Most of my work went into
producing honest empties.
</Callout>

## The threshold is the product

The single highest-leverage line in the service is a comparison:

```python
# Below this, the honest answer is "I don't know" — not a confident synthesis
# from weak evidence. Tuned against a hand-labelled set of unanswerable queries.
if best_score < RETRIEVAL_CONFIDENCE_FLOOR:
    return refusal_with_suggestions(query, candidates)
```

Tuning it was the least glamorous and most valuable week of the project. Too
high and the assistant is useless; too low and it is confidently wrong, which
is worse than useless because it costs the user time to discover.

I built a small evaluation set of questions the corpus genuinely *cannot*
answer, and treated a confident answer to any of them as a hard failure. That
set caught more real regressions than the accuracy metrics did.

## Streaming without lying

Streaming makes latency feel small, and it makes correctness harder: tokens are
already on the user's screen before the answer is complete, so a late-arriving
problem can't be silently swallowed.

Two decisions handled this:

1. **Citations stream inline, attached to the sentence they support** — not
   appended as a bibliography at the end. A user who stops reading halfway has
   still seen sources for what they read.
2. **Retrieval completes before the first token.** It would be faster to
   stream a preamble while retrieving, and it would mean occasionally starting
   an answer the evidence doesn't support.

## What I'd change today

**I'd store the retrieved context with every response.** I log the query and
the answer but not the exact passages, which makes "why did it say that?"
harder than it needs to be. This is the same lesson the NBA project taught me
about immutable raw data, learned twice.

**I'd version the prompt alongside the code.** Prompt changes shipped as config
and are effectively invisible in the git history that matters.

**I'd make the refusal more useful.** "I don't know" is honest but lazy;
"I don't know, but these three documents are adjacent" respects the user's
time. The candidates were right there.

## What I took away

Building a RAG system taught me that the model is the least interesting
component. Retrieval quality, an honest confidence floor, and verifiable
citations decided whether people trusted it — and trust, not accuracy, was
what determined whether they came back.
