## The problem

Every finance dashboard I tried had the same flaw: it showed me a return
percentage I could not reproduce. Different apps gave different answers for the
same account over the same period, and none of them would tell me why.

The product goal followed directly: **every number on the screen must be
traceable to the transactions that produced it.** That constraint drove more of
the architecture than any performance target.

## Why "traceable" is an architectural decision

The naive approach is to compute aggregates and store them. It's fast, and it
makes traceability impossible — once you've stored `return = 8.4%`, the
provenance is gone.

The alternative is to derive everything from an append-only transaction ledger
at read time. That is fully traceable and, done naively, unusably slow: five
years of history recomputed on every page load.

I split the difference with a materialised daily snapshot:

The rule that keeps it honest: **snapshots are never written by hand and never
patched.** If a snapshot is wrong, the ledger is wrong or the derivation is
wrong; both are fixed at the source and the snapshots are rebuilt.

<Callout tone="insight" title="Caches you can rebuild are not scary">
Treating the snapshot table as a disposable cache rather than a second source
of truth removed the entire category of "the aggregate disagrees with the
detail" bugs. When they disagree, the aggregate is simply wrong, and there is
never a debate about which one to trust.
</Callout>

## The tradeoff I made and would make again

Deriving from a ledger means a backfill is expensive. Importing five years of
history for a new account takes tens of seconds, not milliseconds, because
every intervening daily snapshot has to be built.

I chose to make that cost visible rather than hide it: import runs as a
background job with real progress, and the account is marked as still importing
until it completes. Users tolerate a slow import far better than they tolerate
a dashboard that is quietly incomplete.

## Reconciling twelve sources that disagree

Institutions disagree about when a trade "happened". Some report trade date,
some settlement date, some post dividends on the ex-date and some on payment.
Sum them naively and the same portfolio has three different values.

I normalised on **trade date with an explicit settlement offset per source**,
recorded on the source itself rather than inferred:

```ts
// Each source declares its own semantics. Nothing is guessed at parse time.
const SOURCE_SEMANTICS = {
  brokerageA: { basis: "trade", dividendOn: "ex" },
  brokerageB: { basis: "settlement", settlementLagDays: 2, dividendOn: "pay" },
} satisfies Record<string, SourceSemantics>;
```

This is unglamorous and it is the reason the numbers agree. The alternative —
sniffing the convention from the data — worked in testing and failed on the
first source that changed its export format.

## What I'd change today

**I'd model currency from day one.** I assumed a single currency and it is
threaded through the schema as an implicit assumption rather than a column.
Adding multi-currency now means touching the ledger, which is exactly the table
you least want to migrate.

**I'd separate "unrealised" from "realised" earlier.** They were one code path
for too long, and untangling them later was harder than designing them apart.

## What I took away

The dashboard's best feature is a click target: tap any number and see the
transactions behind it. It took the most work and it is the only reason I trust
the thing.

Building it taught me to ask, early and about every displayed value: *if a user
disputes this number, can I show them why it's right?* If the answer is no, the
architecture is wrong, regardless of how fast it renders.
